## Scope and automatic scheduling

The `--phase evaluate --experiment-mode reference-screen` controller loops
over all three registered arms and all three frozen evaluation seeds, launching
three shards per batch. It therefore schedules all 9 batches / 27 shards.

It does **not** run summarize because `evaluate` and `summarize` are separate
controller phases. It also does not contain Stage C, D, or E. Those stages
must not be launched blindly: Stage B must first be summarized, audited,
published, and assigned its frozen scientific terminal state; Stage C must
then pass its natural-data gate before Stage D, and Stage D's frozen decision
controls Stage E.

A fail-closed postprocess watcher is supplied at
`scripts/ops/watch_v5_5_reference_postprocess.sh`. It waits for this exact
controller PID without becoming its parent. After the PID exits it requires:

- exactly 9 `EVAL_COMPLETE` events;
- exactly one evaluate `PHASE_COMPLETE` event;
- exactly 27 evaluation command records;
- exactly 27 shard `metrics.json` files;
- no pre-existing summary output.

Only then does it run the reference-screen summarize phase. It verifies that
the summary and grid audits pass, that exactly 378 task-level rows were
observed, and that `official_test_used` is false. Any mismatch produces a
`FAIL_CLOSED` status and no later stage is started.

## Recovery checkpoints

If only SSH/Codex disconnects, no action is required: reconnect and inspect
the existing PID, log, `EVAL_COMPLETE` count, metrics count, watcher status,
and summary status.

If the RunPod container stops, do not assume the old PID remains meaningful.
Verify every completed batch with the controller's strict resume validator,
archive any incomplete batch and its console logs under
`results/v5_5_full/errors/`, document and publish the interruption, and rerun
only `--phase evaluate` from the frozen source commit. Never overwrite an
incomplete batch or relaunch a parallel service stack.
