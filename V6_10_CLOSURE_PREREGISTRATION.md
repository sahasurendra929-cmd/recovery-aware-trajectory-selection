# V6.10 pipeline-closure preregistration

Preregistered: 2026-07-30 (Asia/Shanghai), before any V6.10 runtime
outcome.

Canonical protocol:

```text
v6_10_pipeline_closure_v1
```

The complete machine-readable contract is
`configs/v6_10_closure.yaml`. If this document and that configuration differ,
the stricter fail-closed interpretation applies and the discrepancy must be
resolved before any runtime attempt.

## 1. Decision and scope

V6 through V6.9 are retained as engineering and protocol-development history.
Their task receipts, smoke outcomes, partial candidate pools, and failure
locations will not be pooled with V6.10.

The 24 tasks repeatedly inspected during V6.4--V6.9 are no longer treated as
a prospective scientific Pilot. They are frozen as a compatibility/development
suite. They may be used to repair implementation classes before the V6.10
release is frozen, but their pass rate, kappa distribution, or teacher
behavior is not evidence for the proposed selector.

V6.10 makes one coordinated scientific closure:

1. successful positive training data are constructed from a sanitized,
   independently replayed oracle reference plan;
2. policy-conditional causal sensitivity is measured separately with a
   gold-free fresh continuation policy;
3. teacher first-action sensitivity is measured by an unforced, unretried
   query rather than inferred from an action inserted by the generator; and
4. the 26 action-identifiable arm-train tasks not used for iterative V6
   repairs become the prospective Pilot.

V6.10 does not claim that the sanitized positive suffix was generated by the
teacher. It does not interpret kappa as policy-invariant causal necessity.
The intended claim is narrower: under a fixed continuation policy and
training budget, policy-conditional forced-first sensitivity can help select
useful recovery training data.

## 2. Research question and primary estimand

The research question is:

> Under a fixed supervised-token and training-compute budget, does selecting
> successful recovery pairs using a frozen combination of forced-first causal
> sensitivity, frozen-base hardness, and coverage improve controlled-error
> end-to-end task success relative to matched stratified-random selection?

The primary official-test estimand is the paired task-level difference

\[
\Delta =
\frac{1}{|T|}
\sum_{t\in T}
\left(
\overline{R}_{t,\mathrm{full}}
-
\overline{R}_{t,\mathrm{random}}
\right),
\]

where the bar averages repeated evaluation seeds for one task. Evaluation
seeds are repeated measurements, not independent tasks. Confidence intervals
will use a task-cluster bootstrap with 10,000 replicates.

The primary metric is controlled-error end-to-end official task success.
Training loss, next-tool-call exact match, token likelihood, and pipeline
completion are diagnostics only.

## 5. Sanitized oracle positive-data construction

V6.9 revealed that a benchmark reference trace may intentionally contain an
unsuccessful lookup followed by a successful correction. Merely allowing such
errors to flow through all replay paths would conflict with the flawless
control and would place additional failed actions inside positive recovery
suffixes. V6.10 therefore separates raw-reference auditing from positive-data
construction.

The model-free preflight artifact protocol is exactly:

```text
v6_reference_execution_preflight_v1
```

It obtains the exact ordered 50-task universe directly from the V6.10
protocol/config and pinned split, before executable registry v2 is built. Its
PASS receipt embeds the sanitized plan and eligibility evidence for every
task. Registry v2 must consume and hash-bind that receipt; the preflight must
not depend on a previously constructed V6.10 registry.

For every formal-universe task, before GPU generation:

1. execute every raw reference action at its exact registered index;
2. retain the complete raw action/result trace;
3. classify a failed reference call as expected only if the exact tool error
   is observed, the agent database hash is unchanged, and the user database
   hash is unchanged when Tau2 exposes one; if no user database exists, the
   before/after evidence must contain explicit null values;
4. remove only those expected, state-preserving failed calls;
5. preserve the original order and exact indices of all retained calls;
6. replay the resulting sanitized plan from the same prefix;
7. require Tau2 `EvaluationType.ENV` reward `1.0` for the raw replay, its
   deterministic repeat, and the sanitized replay;
8. require final agent database hashes and user-database evidence (including
   explicit absence) to equal the successful raw reference replay; and
9. require zero tool errors in the sanitized replay.

This static preflight is deliberately model-free: it runs the environment
component and renderer lint only. It records
`full_official_reward_status = DEFERRED_TO_DYNAMIC_JUDGE`; it does not invoke
the natural-language judge or claim full official task success. Full official
reward is required later for dynamically generated positive trajectories.

If these checks fail, the task receives a typed rejection. The generator must
continue to later tasks; it must not invent a repair trajectory.

Candidate corrective actions must be successful retained slots in the
sanitized plan. Repeated calls with identical name and arguments remain
distinguished by their exact registered action index.

The clean positive view is:

```text
one real user turn
+ complete sanitized reference plan
+ frozen natural completion renderer
```

The recovery positive view is:

```text
the same shared prefix
+ one actually executed, state-preserving injected error
+ the registered successful corrective action
+ the remaining sanitized plan
+ the frozen natural completion renderer
```

The injected failed call and its tool error are prompt context only. No failed
assistant tool call, failed tool result, or additional failed reference call
receives positive loss. Every positive trajectory must obtain official task
success `1.0`, reach the same final state as the sanitized clean trajectory,
and pass independent replay.

## 6. Unforced teacher first-action measurement

Teacher action-switch accuracy is measured independently of positive-data
construction. For each accepted error context, the 72B teacher receives:

```text
shared prefix + actually executed injected failed call + tool error
```

It does not receive reference actions, evaluation criteria, the clean future,
the sanitized completion, or the registered matched action.

Exactly one query is made using the registered branch seed. The first
unretried assistant tool call is compared with the registered matched full
call. A missing, malformed, text-only, or wrong call counts as incorrect.
There is no semantic retry.

For \(N\) accepted candidate pairs, action-switch accuracy is

\[
A_{\mathrm{switch}} =
\frac{1}{2N}
\sum_{p=1}^{N}
\sum_{i=1}^{2}
\mathbf{1}\!\left[\hat a(e_{p,i})=a_{p,i}\right].
\]

The balanced error-blind constant-action baseline is `0.50`.

## 7. Gold-free forced-first causal measurement

For each pair with error contexts \(e_1,e_2\) and matched actions \(a_1,a_2\),
V6.10 executes four cells:

```text
q_e1_a1  q_e1_a2  q_e2_a1  q_e2_a2
```

Only the first assistant tool action is forced. After that tool result, the
same frozen 72B agent policy continues from the observed environment state.
The continuation may see the task instruction, domain policy, tools, user
messages, and observed history. It may not see:

- raw or sanitized reference actions;
- evaluation criteria;
- gold assertions;
- clean-future messages;
- a gold completion renderer; or
- an instruction to execute a remaining oracle plan.

The evaluator may use the frozen task criteria after the rollout ends, but
those criteria are not passed to the agent.

For scientific Pilot and formal measurement, the continuation seeds are:

```text
20260806, 20260807, 20260808
```

There are no semantic retries. With

\[
\overline R(e,a)=\frac{1}{3}\sum_{s=1}^{3}R_s(e,\operatorname{do}(a)),
\]

the policy-conditional forced-first contrast is

\[
\kappa =
\frac{1}{2}
\left[
\overline R(e_1,a_1)+\overline R(e_2,a_2)
-
\overline R(e_1,a_2)-\overline R(e_2,a_1)
\right].
\]

Deterministic reference completion is forbidden inside these four cells.
The matched action may not be silently inserted later by oracle replay.

Compatibility runs use only seed `20260806` to verify the execution pathway;
their kappa values are diagnostic and are never pooled with scientific
measurements.

## 8. GO/NO-GO gates

### 8.1 Compatibility authorization

Compatibility authorizes an immutable V6.10 scientific/static release, not a
selector claim. Each runtime-session release manifest is separately immutable
and authorizes only the exact live model-service process set that it binds.
It requires:

- all 50 formal-universe tasks to have a raw-reference and sanitization audit;
- all 24 compatibility tasks to reach an atomic
  `execution_status=PASS` receipt whose scientific outcome is either
  `ACCEPTED` or a typed `REJECTED`;
- at least 22 compatibility tasks to provide three accepted pairs each;
- all seven historical blocker tasks to pass or produce their exact
  preregistered data-ineligibility rejection rather than an unclassified
  exception;
- zero future leakage;
- zero failed positive labels;
- zero additional failed calls in positive suffixes;
- complete independent replays;
- execution of the genuinely gold-free causal pathway; and
- an unforced teacher first-action receipt for every accepted branch.

Kappa-distribution thresholds are not applied to the development suite.

### 8.2 Prospective Pilot gate

All 26 tasks must reach atomic `execution_status=PASS` receipts with
scientific outcome `ACCEPTED` or typed `REJECTED`. Pilot GO
requires:

- at least 16 tasks with three accepted pairs;
- at least 48 accepted pairs;
- both domains and at least three error families;
- zero future leakage and zero failed positive labels;
- complete matched and independent replay;
- at least 20% of pairs with \(\kappa\ge0.75\);
- at least 20% of pairs with \(\kappa\le0.25\);
- no single kappa bucket above 80%;
- unforced teacher action-switch accuracy at least `0.80`; and
- teacher advantage over the `0.50` error-blind baseline at least `0.20`.

Failure is a preserved V6.10 scientific `NO_GO`. It does not authorize another
task-specific code revision on the same prospective tasks.

### 8.3 Formal pool gate

After Pilot GO, all 50 formal tasks are regenerated in fresh directories.
Formal selection requires:

- at least 48 tasks with three accepted pairs;
- at least 144 accepted pairs;
- both domains and at least three error families;
- the complete Pilot identifiability gate applied again;
- one atomic, hashed candidate pool frozen before measurement and scoring.

Forty to 47 qualifying tasks authorize a screen only and no formal claim.
Fewer than 40 tasks stop the experiment.

## 9. Failure and continuation semantics

The runner must not stop at the first task-local incompatibility. It records a
typed rejected-task receipt and continues for:

- raw or sanitized reference failure;
- final-state mismatch;
- insufficient successful corrective calls;
- an injected error that is not real and state-preserving;
- matched positive construction failure;
- task-local replay failure; or
- an unsupported task-local assertion.

The entire run aborts for:

- official-test access;
- source, container, benchmark, split, registry, or config drift;
- model-server identity drift;
- future leakage;
- single-shard task overlap or missing registered coverage;
- artifact corruption; or
- an unclassified exception.

An infrastructure interruption may restart an incomplete task-worker process
at most twice, using the exact same seed and semantic contract within the same
live model-service session. Partial task output is quarantined. This allowance
never permits a teacher/user/judge model-service restart: model-service
identity drift aborts the current attempt, and a later run requires a new
runtime service session and generation attempt. Scientific rejection is not
an execution failure: a completely audited typed rejection has
`execution_status=PASS`, `scientific_outcome=REJECTED`, and does not consume a
restart.

## 10. Provenance, resume, and attempt identity

Every run and task receipt must bind:

- source and Tau2 checkouts with no tracked or untracked drift, plus the clean
  source commit and release-tree hash;
- hashes of relevant scripts, this preregistration, and the config;
- operator-declared pinned container-image digest (cross-bound across all
  artifacts, not misreported as a live observation), hash of the current
  requirements specification, and observed runtime/library versions;
- Python, Torch, CUDA, driver, and vLLM versions;
- GPU model, UUID, and memory;
- Tau2 commit, clean-tree state, split hash, and task-file hashes;
- model-server receipt hashes, live PID/start identity, endpoint-socket
  ownership, exact safe argv, GPU visibility, and local snapshot identity;
- exact command, UTC start/end, task/shard map, and all seeds;
- semantic-generation-contract hash;
- parent artifact hashes; and
- official-test seal state.

An API endpoint address or `/models` name is transport metadata, not proof of
model identity. The receipt builder and generator must bind the endpoint to
the live process that owns its listening socket, the frozen local HF snapshot
and content-addressed weight blobs, and the declared GPU UUIDs. Dummy/adapter/
alternate-tokenizer or otherwise unregistered semantic launch flags are
forbidden.

A runtime service session denotes one exact live teacher/user/judge process
set. Its runtime session ID is an operational namespace, not identity
evidence; the authoritative identity is the PID/start, executable, argv,
snapshot, socket, GPU, probe, and receipt hashes. Restarting any model service
closes the current session. The next generation run must use a new runtime
session ID, new runtime receipts and release manifest, and a fresh generation
attempt directory. When the source, Tau2 checkout, split, configuration,
preregistration, and their hashes are unchanged, the immutable reference
preflight and executable registry remain reusable across runtime sessions.
Runtime receipts, release manifests, run contracts, and task receipts never
cross runtime sessions.

The current file named `requirements-stage0-v5.txt` is a requirements
specification, not a fully resolved transitive lock with wheel hashes. The
legacy receipt field `dependency_lock_sha256` binds its exact bytes but must
not be described as full environment reproducibility. Formal paper runs
require either a fully resolved lock/wheel manifest or an explicitly archived
installed-package freeze in addition to the observed runtime receipt.

Resume is permitted only inside the same attempt and runtime service session
with identical source, container, model receipts, registry, semantic contract,
task map, seeds, decoding, and budgets. Only atomic bundles with
`execution_status=PASS` may be reused; this includes both scientifically
accepted and completely audited typed-rejected outcomes. Incomplete or
infrastructure-failed execution is never resumable.
Compatibility receipts cannot be reused in Pilot; Pilot receipts cannot be
reused in formal generation; receipts from different source commits cannot be
merged.

Attempt names have the form:

```text
v6_10-{stage}-a{NN}-{UTC timestamp}
```

An attempt number is not a design version. A task-specific runtime failure
must not create V6.11.

## 11. Official evaluation and claim rule

The official test is unsealed once, only after the candidate pool, measured
scores, selector manifests, materialized data, all checkpoints, checkpoint
selection, evaluator, and statistical summarizer are frozen and hashed. The
unseal event must emit `official_test_unseal_receipt.json`. No code, model,
metric, threshold, or checkpoint decision may change afterward.

The primary comparison is `full_proposed - random_stratified` under matched
supervised-token budgets. Clean behavior is evaluated with the preregistered
non-inferiority margin `-0.05`.

A positive V6.10 claim requires official end-to-end task success, a paired
task-level delta, a task-cluster confidence interval, and clean
non-inferiority. A successful data pipeline, a positive point estimate,
lower training loss, or higher next-call exact match alone is insufficient.

## 12. Runtime authorization

This document authorizes implementation and code-only tests. It does not by
itself authorize a paid Pilot.

Runtime compatibility may start only after:

1. the implementation exposes separate sanitized-positive, unforced-probe,
   and gold-free-causal pathways;
2. an end-to-end `retail:35` regression reaches label materialization rather
   than testing only reference execution;
3. tests prove no causal cell can call a deterministic reference-completion
   helper;
4. source/container/model receipts are bound into run and task contracts;
5. task-local rejection-and-continue plus exact single-shard terminal closure
   are tested;
6. stale controller/progress metadata are replaced by one generated release
   manifest; and
7. the complete code-only suite passes from a clean checkout.
